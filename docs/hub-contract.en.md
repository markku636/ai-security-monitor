# Agent ↔ Hub contract

English | [繁體中文](hub-contract.md)

The HTTP interface between `ai-security-monitor` (the agent) and Security Hub. The single source of truth is `agent/src/hub/contract.rs` and
`agent/src/model/*`; `contract/*.v1.json` is generated by a Rust test and validated by the hub's zod schemas
(`hub/lib/ingest/schema.ts`) in vitest, so CI fails as soon as either side drifts.

To change the format on purpose:

```bash
cd agent && ASA_UPDATE_CONTRACT=1 cargo test contract   # regenerate contract/*.v1.json
# then update hub/lib/ingest/schema.ts and run: cd hub && npm test
```

## Common rules

| Item | Rule |
|---|---|
| Auth | `Authorization: Bearer <client key>` (one of `AI_SECURITY_MONITOR_HUB_CLIENT_SECRETS`; enroll keys behave the same) |
| Identity | `X-ASA-Agent-Id` (must equal the agent id in the body, else 400 `agent_id_mismatch`), `X-ASA-Agent-Version` |
| Compatibility | The `X-ASA-*` headers and the `asa_` / `asa_ek_` token prefixes intentionally survived the rename, so 0.1.x agents and the new Hub interoperate; Hub variables `AI_SECURITY_MONITOR_HUB_*` also accept the old `ASA_HUB_*` names |
| Identity pinning | `X-ASA-Agent-Token`: a random token generated at enroll time. The hub stores its sha256 the first time it sees it and answers 403 `agent_token_mismatch` afterwards if it differs (client keys are shared between hosts, so this is what stops impersonation). Unenrolling keeps the token |
| Compression | `Content-Encoding: gzip` for bodies > 16 KB; ≤ 4 MB compressed, ≤ 24 MB decompressed (else 413) |
| Structure limits | depth, node count, string length, array length, key count; `__proto__`/`constructor`/`prototype` are rejected → 400 with the rule name only |
| Transport | https; plain http only for loopback and private addresses (`ai-security-monitor enroll --insecure-http` to override) |

Error handling on the agent:

| Status | Meaning | Agent action |
|---|---|---|
| 401 / 403 | key rejected | stop uploading; run `ai-security-monitor enroll` again |
| 400 / 413 / 422 | payload rejected (a retry would fail too) | drop it, never queue it |
| 429 | too frequent (`Retry-After`) | queue the report in the outbox, retry next round |
| 5xx / unreachable | hub temporarily down | queue the report in the outbox (keeps the newest 50) |

## Endpoints

### `POST /api/v1/agents/register`

Body: `contract/register.v1.json` (`agent` identity, `accept_remote_actions`, `service_mode`).
Response: `{ agent_id, created, hub: { name, version, min_report_interval_s, snapshot_interval_s, max_report_bytes, server_time } }`.
`ai-security-monitor enroll` calls `/api/health` first and only stores the key (OS keychain or a 0600 file) after registration succeeds.

### `POST /api/v1/ingest/report`

Body: `contract/report.v1.json` (a full scan report).
- Idempotent on `report_id`: a report already received returns `duplicate: true` **without being throttled**, so outbox retries never get stuck.
- Throttling uses the report's `finished_at`: two reports from the same agent must be at least `AI_SECURITY_MONITOR_HUB_INGEST_MIN_INTERVAL_MS`
  apart (default 60 s). Reports queued while the hub was down are one scan interval apart and drain in one go; there is also a hard cap of 30 reports per agent per minute.
- Response: `{ ok, report_id, duplicate, findings: { new, updated, unchanged, reopened, resolved }, min_interval_ms, server_time }`.

### `POST /api/v1/ingest/snapshot`

Body: `contract/snapshot.v1.json` (current connections and listeners, each connection with direction and verdict). Replaces the agent's latest
connections and aggregates destinations (keeping the worst verdict). Optional `dns_names` (public remote IP → domains this computer resolved, up to 20 per IP; only IPs present in the snapshot are kept) is stored in `ip_domains` for "Domains on this IP" on the IP page. Minimum interval `AI_SECURITY_MONITOR_HUB_SNAPSHOT_MIN_INTERVAL_MS` (default 10 s). Unregistered agents get 409.

### `POST /api/v1/ingest/metrics`

Body: `contract/metrics.v1.json` `{ agent_id, performance, samples: [{ ts, interval_s, net: { rx_bytes, tx_bytes, interfaces[], processes?, process_source? }, perf? }] }`, 1–240 samples per batch, ≤ 1 MB compressed. `performance` says whether this computer turned performance collection on (the Hub cannot turn it on); `perf` is present only then.
- (agent, `ts`) is unique: re-sending (the agent's offline queue) never double counts; future timestamps are clamped to now; samples older than `AI_SECURITY_MONITOR_HUB_METRICS_RAW_DAYS` (default 7 days) are ignored.
- Throttling uses the newest sample time of the batch (same minimum interval as snapshots), so queued older batches are not blocked. Unregistered agents get 409.
- Response: `{ ok, stored, duplicate, stale, performance, server_time }`. When an older Hub does not have the endpoint (404), the agent keeps the samples and retries after 30 minutes.
- Details and retention: [metrics.en.md](metrics.en.md).

### `POST /api/v1/ingest/dns`

Body: `contract/dns.v1.json` `{ agent_id, records: [{ ts, name, registrable?, qtype, rcode, process?, exe?, pid?, count, answers[], cnames[], source }] }`, 1–1000 records per batch, ≤ 2 MB compressed. Each record is the background DNS collector's per-minute aggregate by (domain, type, result, program); only hosts with `dns.upload = all` send them.
- (agent, `ts`, `name`, `qtype`, `rcode`, `process`, `source`) is unique: re-sending overwrites instead of double counting; records older than `AI_SECURITY_MONITOR_HUB_DNS_RAW_DAYS` (default 7 days) are ignored; hourly rollups are kept for `AI_SECURITY_MONITOR_HUB_DNS_HOURLY_DAYS` (default 90 days).
- `registrable` is the registrable domain the agent computed from the Public Suffix List (the Hub falls back to the last two labels).
- Response: `{ ok, stored, stale, domains, server_time }`. When an older Hub does not have the endpoint (404), the agent keeps the records and retries after 30 minutes.

### Protective DNS (`dns-server --hub`)

Identity: a dns token (a web-created API token with the "Protective DNS server" permission, or `AI_SECURITY_MONITOR_HUB_DNS_TOKEN` from compose, at least 32 characters), or an enrolled computer's own client key (`X-ASA-Agent-Id`, subject to identity pinning). A dns token can also download the intel mirror (`/api/v1/feeds/*`).
- `GET /api/v1/dns/config`: `{ blocking, enabled, paused_until, upstreams[], feeds[], min_confidence, block[], allow[], internal_suffixes[], block_private_relay, log, resolver_ips[], etag, server_id }`. Returns 304 for a matching `If-None-Match`. `blocking` = on and not paused; when off or paused the dns-server keeps forwarding. The dns-server polls every minute and keeps the last copy in `dns-server/hub-config.json` (after a restart it follows the last settings even if the Hub is unreachable). `resolver_ips` are the "DNS addresses devices should use": enrolled computers also fetch the config with their own client key every 10 minutes (saved as `dns/hub-protect.json`) for `dns use-hub` and `dns.not_protected`.
- `POST /api/v1/dns/heartbeat`: `contract/dns-heartbeat.v1.json` `{ version, hostname, status }` (`status` is the same as `dns-server --status`, ≤ 32 KB), every 30 seconds. Response `{ ok, server_id, config_etag, blocking, server_time }`; when `config_etag` differs from the dns-server's copy it fetches the config right away.
- `POST /api/v1/dns/queries`: `contract/dns-resolver.v1.json` `{ records: [{ ts, name, registrable?, qtype, rcode, process?, count, answers[], client, source: "resolver" }] }`, 1–1000 records per batch, ≤ 2 MB compressed. Each record is a per-minute aggregate by (client, domain, type, result); when `rcode` is `BLOCKED`, `process` names the list that blocked it. (server, `ts`, `client`, `name`, `qtype`, `rcode`) is unique and re-sending overwrites; the Hub maps clients to hosts by the IPs hosts report (unmapped = a device without an agent); retention follows `AI_SECURITY_MONITOR_HUB_DNS_RAW_DAYS`. Response `{ ok, stored, stale, mapped, server_time }`.

### `POST /api/v1/agents/me/heartbeat`

Body: `{ agent_id, ts, version, uptime_s?, last_scan_at?, elevated, intel_checked_at?, intel_feeds?, update?, advertising? }`. Unknown agents get 404.

- `update` (0.4.0+): `{ mode: "off"|"notify"|"auto", owner: "agent"|"desktop", latest?, available, checked_at?, note? }` — the automatic-update
  setting, who installs updates (`desktop` for the agent built into the desktop app) and the latest version found; stored in `agents.update_info`,
  the host list shows "New version".
- `advertising` (0.4.0+): `{ url, state: "advertising"|"hub_unreachable"|"starting"|"error", fingerprint?, error?, since? }` — which Hub this
  computer's background service advertises on the LAN (`hub.advertise_url`); stored in `agents.advertising`; "Add a host" counts rows from the last
  15 minutes whose fingerprint matches.
- When either is missing (older agents, the heartbeat sent by `upload`) the previous value is kept.

### Remote actions

After an admin approves an action on the hub (currently `block_ip`, `unblock_ip`, `close_port`; `close_port` is destructive and needs the hostname typed in):

1. When the agent registers with `accept_remote_actions: true` and a pinned identity, the response carries `action_key` = HMAC-SHA256(hub signing key, `asa-action-key|<agent_id>`), stored in the OS keychain.
2. When a heartbeat reports `pending_actions` > 0, the agent calls `GET /api/v1/agents/me/actions` and receives `{action_id, agent_id, kind, params, expires_at, token}`.
3. The agent checks: `token` = HMAC-SHA256(action_key, canonical JSON of {action_id, agent_id, kind, params, expires_at}) (sorted keys, no whitespace; see `contract/action.v1.json`), matching agent id, not expired (24 h after approval), kind allowed by local settings (block_ip / unblock_ip by default; destructive ones need `allow_destructive`), target not on the local allowlist or a known-good list and not covering a local interface address.
4. Background runs never pop UAC or sudo: without administrator rights the action is reported as failed. Results go to `POST /api/v1/agents/me/actions/{id}/result` (`{agent_id, ok, output}`). Actions not reported within 10 minutes are dispatched again; the agent de-duplicates by action id and re-sends the earlier result.

Signing key: `AI_SECURITY_MONITOR_HUB_ACTION_SIGNING_KEY` (or `_FILE`); if unset, one is generated on first use and stored in the database. After changing it, agents must register again to get the new `action_key`.

### Keyless enrollment

Agents can join without an enroll key: they send an enrollment request, an admin approves it in the Hub (or the source IP is inside an
auto-approve network), and the agent then gets an enroll key bound to its own agent id. How to use it: [enrollment.en.md](enrollment.en.md).
All binary values are base64url without padding; fingerprints/codes are RFC 4648 base32.

- **Hub identity** – `GET /api/v1/hub/identity[?nonce=<16–128 chars [A-Za-z0-9_-]>]` (public). Response: `contract/hub-identity.v1.json`
  `{ name, version, edition, algorithm: "ed25519", public_key, fingerprint, enrollment: { keyless, mode }, nonce?, signature? }` (`mode`: `auto`|`review`, since 0.5).
  `fingerprint` = first 20 base32 characters of SHA-256(raw 32-byte public key), in groups of 4 (`72AS-YEXT-VNGO-NLC5-W2NM`);
  `signature` = Ed25519 over `asa-hub-identity|v1|<nonce>|<fingerprint>`. The key pair is generated once and stored in `settings.hub_identity`.
  120 requests/min per IP.
- **Request** – `POST /api/v1/agents/enroll-request` (no Authorization). Body: `contract/enroll-request.v1.json`
  `{ agent, accept_remote_actions, request_secret (43–128 chars), hub_fingerprint? }`. Response 201 (200 when the same agent + secret repeats):
  `{ request_id, status, auto_approved, request_code, poll_interval_s, expires_at, hub: { name, version, fingerprint } }`.
  `request_code` = first 8 base32 characters of SHA-256(`asa-enroll-code|<request_secret>`) as `XXXX-XXXX`; the agent computes it locally too.
  Errors: 403 `enroll_requests_disabled` (`AI_SECURITY_MONITOR_HUB_ENROLL_REQUESTS=0`), 409 `hub_fingerprint_mismatch` `{fingerprint}`,
  429 `too_many_requests` (120 per IP per 10 min), 503 `too_many_pending` (500 pending), 400 `bad_request` `{rule}`.
  Only the secret's SHA-256 is stored. Auto-approval uses the TCP peer address (hooked in the Hub's HTTP server) — X-Forwarded-For only when
  `AI_SECURITY_MONITOR_HUB_TRUST_PROXY` is on; agents that already exist but never pinned a token are never auto-approved.
- **Poll** – `GET /api/v1/agents/enroll-request/{id}` with `Authorization: Bearer <request_secret>`. Response: `contract/enroll-status.v1.json`
  `{ request_id, status: pending|approved|rejected|expired, request_code, poll_interval_s, expires_at, reason?, credentials? }`.
  Unknown id and wrong secret both return 404 (constant-time comparison); 30 failures per IP per 10 min → 429.
  `credentials` = `{ agent_id, client_key, hub_fingerprint, signature }` only while approved, not revoked and not yet claimed (or claimed less than
  10 minutes ago); `signature` = Ed25519 over `asa-enroll-approved|v1|<request_id>|<agent_id>|<sha256hex(client_key)>`, verified by the agent with
  the public key it pinned before sending the request. `client_key` is an `asa_ek_…` enroll key derived from a Hub secret (never stored in clear)
  and **bound to that agent id**: using it for another agent id returns 403 `key_bound_to_other_agent` on every agent endpoint.
- The agent then calls `POST /api/v1/agents/register` exactly as with a normal key (`X-ASA-Agent-Token` pinning unchanged); the first successful
  register marks the request as claimed. Pending requests expire after 7 days; approved but unclaimed ones also expire (and their key is revoked).
- **Admin** (session + CSRF, or admin Bearer): `GET /api/v1/admin/enroll-requests?status=pending|all` (never returns secrets or keys),
  `POST /api/v1/admin/enroll-requests/decide` `{ ids[1..200], decision: approve|reject, reason? }`,
  `GET|PUT /api/v1/admin/enroll-settings` `{ join_mode?: "auto"|"review", auto_approve_cidrs?[≤64] }` (either field alone is fine; `join_mode` returns 409 `locked_by_env` when an environment variable sets it; GET also returns `join_mode_source: env|settings|default`; IPv4 prefix ≥ /8, IPv6 ≥ /16; the GET also reports mDNS status and the
  SRV/TXT records to add, named `_aisecmon._tcp.<domain>`). Audit: `enroll_request.created|approved|rejected|auto_approved|auto_capped`, `enroll_settings.updated` (`target_id` = `enroll_join_mode` / `enroll_auto_approve_cidrs`). Automatic approvals record `decided_by` = `auto:all` (automatic mode) or `auto:<network>`.
- **Agent side**: the Hub fingerprint is pinned in `config.json` (`hub.fingerprint`, `hub.public_key`). `watch` checks
  `/api/v1/hub/identity` at start and stops uploading if it differs; a pending request lives in `<config>/hub-enroll-request.json` (secret in the
  keychain / secrets file) and `watch` keeps polling it.

## `ai-security-monitor watch` loop

1. Load config and key → `register` (identity and version are refreshed on every start).
2. Every `snapshot_interval` (default 1 min): take a connection snapshot (with intel verdicts) → `ingest/snapshot`, then `heartbeat`; pending remote actions are fetched, verified, executed and reported.
   Every `metrics.interval` (default 1 min): take a traffic (+ performance) sample → queue it in `metrics/queue.jsonl` → `ingest/metrics` (up to 3 batches of 120 per round).
3. Every `interval` (default 10 min): flush queued reports first (stop at the first retryable error) → scan → `ingest/report`; queue it on failure.
4. The latest report is saved to `<config>/reports/latest.json`; `ai-security-monitor status` shows hub health, queued reports and the last scan.
5. Automatic updates (`update.mode` not `off`): check GitHub Releases at most once a day; with `auto` in a background service (`--service`), download, verify, replace and restart.
6. With `hub.advertise_url` set: keep advertising that Hub over mDNS in the background (its identity is checked every minute; advertising pauses while it is unreachable); the state goes into the heartbeat's `advertising`.

`--once` runs a single round (handy for schedulers and tests; no update checks, no advertising); `--no-upload` scans locally only. `ai-security-monitor upload`
is a manual round: flush the outbox, snapshot, full report, heartbeat, and print the result.
