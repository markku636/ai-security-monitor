# Agent ↔ Hub contract

English | [繁體中文](hub-contract.md)

The HTTP interface between `ai-security-monitor` (the agent) and Security Hub. The single source of truth is `agent/src/hub/contract.rs` and
`agent/src/model/*`; `contract/*.v1.json` is generated by a Rust test and validated by the hub's zod schemas
(`hub/lib/ingest/schema.ts`) in vitest, so CI fails as soon as either side drifts.

To change the format on purpose:

```bash
cd agent && ASA_UPDATE_CONTRACT=1 cargo test contract   # regenerate contract/*.v1.json
# then update hub/lib/ingest/schema.ts and run: cd hub && npm test
```

## Common rules

| Item | Rule |
|---|---|
| Auth | `Authorization: Bearer <client key>` (one of `AI_SECURITY_MONITOR_HUB_CLIENT_SECRETS`; enroll keys behave the same) |
| Identity | `X-ASA-Agent-Id` (must equal the agent id in the body, else 400 `agent_id_mismatch`), `X-ASA-Agent-Version` |
| Compatibility | The `X-ASA-*` headers and the `asa_` / `asa_ek_` token prefixes intentionally survived the rename, so 0.1.x agents and the new Hub interoperate; Hub variables `AI_SECURITY_MONITOR_HUB_*` also accept the old `ASA_HUB_*` names |
| Identity pinning | `X-ASA-Agent-Token`: a random token generated at enroll time. The hub stores its sha256 the first time it sees it and answers 403 `agent_token_mismatch` afterwards if it differs (client keys are shared between hosts, so this is what stops impersonation). Unenrolling keeps the token |
| Compression | `Content-Encoding: gzip` for bodies > 16 KB; ≤ 4 MB compressed, ≤ 24 MB decompressed (else 413) |
| Structure limits | depth, node count, string length, array length, key count; `__proto__`/`constructor`/`prototype` are rejected → 400 with the rule name only |
| Transport | https; plain http only for loopback and private addresses (`ai-security-monitor enroll --insecure-http` to override) |

Error handling on the agent:

| Status | Meaning | Agent action |
|---|---|---|
| 401 / 403 | key rejected | stop uploading; run `ai-security-monitor enroll` again |
| 400 / 413 / 422 | payload rejected (a retry would fail too) | drop it, never queue it |
| 429 | too frequent (`Retry-After`) | queue the report in the outbox, retry next round |
| 5xx / unreachable | hub temporarily down | queue the report in the outbox (keeps the newest 50) |

## Endpoints

### `POST /api/v1/agents/register`

Body: `contract/register.v1.json` (`agent` identity, `accept_remote_actions`, `service_mode`).
Response: `{ agent_id, created, hub: { name, version, min_report_interval_s, snapshot_interval_s, max_report_bytes, server_time } }`.
`ai-security-monitor enroll` calls `/api/health` first and only stores the key (OS keychain or a 0600 file) after registration succeeds.

### `POST /api/v1/ingest/report`

Body: `contract/report.v1.json` (a full scan report).
- Idempotent on `report_id`: a report already received returns `duplicate: true` **without being throttled**, so outbox retries never get stuck.
- Throttling uses the report's `finished_at`: two reports from the same agent must be at least `AI_SECURITY_MONITOR_HUB_INGEST_MIN_INTERVAL_MS`
  apart (default 60 s). Reports queued while the hub was down are one scan interval apart and drain in one go; there is also a hard cap of 30 reports per agent per minute.
- Response: `{ ok, report_id, duplicate, findings: { new, updated, unchanged, reopened, resolved }, min_interval_ms, server_time }`.

### `POST /api/v1/ingest/snapshot`

Body: `contract/snapshot.v1.json` (current connections and listeners, each connection with direction and verdict). Replaces the agent's latest
connections and aggregates destinations (keeping the worst verdict). Minimum interval `AI_SECURITY_MONITOR_HUB_SNAPSHOT_MIN_INTERVAL_MS` (default 10 s). Unregistered agents get 409.

### `POST /api/v1/agents/me/heartbeat`

Body: `{ agent_id, ts, version, uptime_s?, last_scan_at?, elevated }`. Unknown agents get 404.

### Remote actions

After an admin approves an action on the hub (currently `block_ip`, `unblock_ip`, `close_port`; `close_port` is destructive and needs the hostname typed in):

1. When the agent registers with `accept_remote_actions: true` and a pinned identity, the response carries `action_key` = HMAC-SHA256(hub signing key, `asa-action-key|<agent_id>`), stored in the OS keychain.
2. When a heartbeat reports `pending_actions` > 0, the agent calls `GET /api/v1/agents/me/actions` and receives `{action_id, agent_id, kind, params, expires_at, token}`.
3. The agent checks: `token` = HMAC-SHA256(action_key, canonical JSON of {action_id, agent_id, kind, params, expires_at}) (sorted keys, no whitespace; see `contract/action.v1.json`), matching agent id, not expired (24 h after approval), kind allowed by local settings (block_ip / unblock_ip by default; destructive ones need `allow_destructive`), target not on the local allowlist or a known-good list and not covering a local interface address.
4. Background runs never pop UAC or sudo: without administrator rights the action is reported as failed. Results go to `POST /api/v1/agents/me/actions/{id}/result` (`{agent_id, ok, output}`). Actions not reported within 10 minutes are dispatched again; the agent de-duplicates by action id and re-sends the earlier result.

Signing key: `AI_SECURITY_MONITOR_HUB_ACTION_SIGNING_KEY` (or `_FILE`); if unset, one is generated on first use and stored in the database. After changing it, agents must register again to get the new `action_key`.

## `ai-security-monitor watch` loop

1. Load config and key → `register` (identity and version are refreshed on every start).
2. Every `snapshot_interval` (default 1 min): take a connection snapshot (with intel verdicts) → `ingest/snapshot`, then `heartbeat`; pending remote actions are fetched, verified, executed and reported.
3. Every `interval` (default 10 min): flush queued reports first (stop at the first retryable error) → scan → `ingest/report`; queue it on failure.
4. The latest report is saved to `<config>/reports/latest.json`; `ai-security-monitor status` shows hub health, queued reports and the last scan.

`--once` runs a single round (handy for schedulers and tests); `--no-upload` scans locally only.
